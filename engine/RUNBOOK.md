## 手順

1. **リポジトリを用意する**
   ```
   cd ~ && (test -d xrp-forecast/.git || git clone --depth 1 https://github.com/naoki6154-jpg/xrp-forecast xrp-forecast)
   cd xrp-forecast && git pull -q --rebase
   cat handoff.md | tail -20 ; head -c 600 state/latest.json
   ```
   リポジトリがこのセッションにない場合は add_repo（access: push）で追加してから clone する。
2. **実行の名前を決める**：`MODE` は朝なら `morning`、夜なら `night`、それ以外は `manual`。
   ```
   RID=$(TZ=Asia/Tokyo date +%Y%m%d-%H%M)-$MODE ; echo $RID
   ```
3. **メインの開始を記録**：`python3 engine/dash_ops.py runlog --agent main --phase start --run-id $RID --mode $MODE`
   の出力（JSONの配列）を、そのまま db_write の ops に渡す（slug は上記）。
4. **①数値データ担当の点検**：`python3 engine/dash_ops.py numeric-check --run-id $RID --mode $MODE` の出力を db_write。
   （取得そのものは GitHub Actions と東京の Cloud Run が行う。ここでは保存済みデータの成否と新しさを数える）
4b. **イベント結果の確認（毎回・全モード）**：ledger/calendar.csv で、前回の実行から今回までの間に発表時刻が過ぎたイベント（CPI・FOMC・雇用統計など）を探す。
   ledger/results.csv に結果が入っていれば、手順5の engine/events_sync.py が自動で確定扱いにして再計算する（定時の4回が、そのまま「イベント後の更新」になる。発表の最長6時間後に反映）。
   結果が入っていなければ、報告に「📰 イベント台帳に〇〇の結果の登録を頼む」と1行書く。予想は結果なしで出してよい。
4c. **最新情報の収集（毎回・全モード・省略しない。2026-11-15に利用者の指示で追加）**：最新の情報がなければ予想はできない。手順5の前に、次の全てを取る。
   取り方は WebSearch／WebFetch（一次情報を優先）。保存データ（state/・data/）で足りるものは使う。新しさの基準はデータの性質で分ける（2026-11-17 修正。以前は一律6時間で、日次データが毎回「古い」扱いになり、一部失敗が続いた）：毎時のデータ（BTC・XRPの価格、資金調達率、ドル円）は2時間以内。日次のデータ（ETF・FRED・恐怖強欲指数。取得は1日2回＝朝8:30ごろ・夜20:30ごろ）は、直近の営業日（または当日）の値が入っていれば「新しい」。BTC・ETHの価格はまず保存データ（Binance 1時間足・Kraken）を使い、WebSearch は補う用途にする。2025年の記事は使わない（日付を必ず確認）。
   - **ETFの資金の流れ**：検索ではなく保存データを読む（2026-11-21 変更）。XRP＝`data/raw/flows/etf_flows_xrp.csv`（SoSoValue API、毎日08:30・20:30 JST取得、2026-10-22以降）、BTC＝`etf_flows_btc.csv`・ETH＝`etf_flows_eth.csv`（Farside、1日2回）。**最新の行の日付を必ず表示する**。直近の米国営業日の行がまだ無いのは、取得時刻（米国の発表後の08:30）より前なら「未公表」で失敗に数えない。08:30の取得後も前営業日の行が無ければ「取れなかった」とし、🗄️データ基盤に知らせる。The Block・CoinGlass は利用規約が自動収集を禁止しているので使わない。
   - **経済指標の結果**：前回の実行から今回までに発表されたもの（CPI・PPI・雇用統計・PCE・小売売上・FOMC・日銀 など）。値・予想・前回値・発表時刻・出典を付ける。
   - **価格・市況**：BTC・ETHの価格と直近の安値・高値、ドル円、米国株（ナスダック・S&P500）、暗号資産の清算額、恐怖強欲指数。
   - **ニュース**：XRP・リップル・暗号資産の規制（CLARITY法など）、地政学（イラン情勢）、大企業の重大ニュース（エヌビディアなど）で、前回から動いたもの。
   取れた分は、ダッシュボードの `config/watch`（経済指標の結果・ETFの行・BTCの200日線）に db_write（merge）で反映する。価格・ETF・結果の数字はプログラムの予想に入らない参考表示なので、**AIが数字を作らない**（取れない値は空欄にして理由を書く）。
   経済指標の結果が `ledger/results.csv` に無ければ、報告に「📰 に〇〇の登録を頼む」と書く（利用者の指示があるときだけ司令塔が代行して追記してよい）。
   **経済指標の結果**は、先に `engine/events.json` と `ledger/` の予定表で「前回の実行から今回までに発表予定があったか」を確かめる。予定が無ければ「該当なし（取得済み扱い）」とし、失敗に数えない。予定があって結果が見つからないときだけ「取れなかった」にする。WebSearch は検索語に日付（例：「November 16 2026」）を入れ、ページが分かっているものは WebFetch で直接読む。日付が確認できない記事は使わない。
   **取れなかった必須項目（ETF・経済指標の結果・BTC価格のどれか）があるときは、予想は出すが、状態を「一部失敗」にし、報告の1行目に【要対応】と取れなかった項目を書く**（ダッシュボードには「最新情報が未取得」と出す）。取れた項目と取れなかった項目は、runlog の note に書く。
5. **予想エンジンを実行**：
   ```
   python3 engine/run.py --mode $MODE --run-id $RID
   ```
   失敗したら、エラーの最後の数行をメモして手順9へ（状態は「失敗」）。
6. **ダッシュボードに予想を書く**：`python3 engine/dash_ops.py update` の出力を、そのまま db_write の ops に渡す。
   1文字も変えない（数字を丸めたり要約したりしない）。書けなかったら1回だけやり直し、だめなら「一部失敗」。
7. **（朝だけ）画面の変更履歴を handoff.md に書き写す**：利用者がダッシュボードの「編集」で変えた内容は、ダッシュボードの履歴にしか残らないため。
   - db_query で collection `changelog` を `orderBy: -at`、`limit: 50` で読む。
   - `by` が「利用者」で始まるものだけを選ぶ（チャットが書いた分は、そのチャットが handoff.md に書いている）。
   - そのうち、handoff.md にまだ `changelog/<文書のid>` の文字列が無いものを、古い順に1件1行で、handoff.md の**末尾に追記**する（書き換えない）。
     形式：`- YYYY-MM-DD HH:MM JST［利用者（ダッシュボードの編集）］<what の内容>（changelog/<文書のid>。朝の定時更新が書き写し）`
   - 該当が無ければ何もしない。夜の更新では行わない。
8. **記録をGitHubに保存**（forecasts/ と、朝に書き写した場合の handoff.md だけ）：
   ```
   git add forecasts/ handoff.md && git commit -q -m "forecast: $RID" && git pull -q --rebase && git push -q
   ```
   pull でぶつかったら、`git rebase --abort` で止め、相手の変更を消さずに報告する（push しない）。
9. **メインの終了を記録**：
   ```
   python3 engine/dash_ops.py runlog --agent main --phase end --run-id $RID --mode $MODE --status 成功 --duration <秒> --ok-items <書けた期間の数> [--failed 項目,項目] [--note "..."]
   ```
   状態は 成功／一部失敗／失敗 のどれか。出力を db_write。
10. **報告**：`engine/out/summary.txt` の内容を、そのまま報告する。異常（失敗、代わりの取得先、モデル間の差が大きい、データが古い）があれば先頭に書く。
    **異常があったときは、1行目に「どのチャットに何と頼めばよいか」を書く**（下の「止まったときの対応」の表から選ぶ）。
    例：`【要対応】🗄️ データ基盤に「jp_relayの取得が失敗しています。直して」`
   朝の実行で異常があったとき、または前回より「1週間後に上がる確率」が10ポイント以上動いたときは、プッシュ通知を送る。
   summary.txt の1行目が【通知】で始まるとき（engine/alerts.py の「重要」）は、その行をそのまま報告の1行目に置き、プッシュ通知を送る（1.2版から）。

## よくある失敗

| 症状 | 対応 |
| --- | --- |
| db_write が拒否された | 1回だけやり直す。だめなら状態「一部失敗」で終了し、報告に書く |
| db_write のツールが見つからない | ToolSearch で「db_write」を探して読み込む。無ければ ArtifactData（url https://claude.ai/artifact/Gx6ZDpofZMFHSSC1zMLzi2）で同じ内容を書く。これは失敗に数えない（11/16〜18に失敗扱いされていた） |
| ダッシュボードにどちらの方法でも書けなかった | forecasts/ への保存は行い、状態「一部失敗」で報告の1行目に【要対応】と書く。**次の実行は、最初に直近の forecasts/ の run_id に runs/<run_id>_main_end が無いかを確かめ、無ければ「後から記録」として runs に補記する**（11/15 18:10 はGitHubに予想があるのにダッシュボードに記録が無かった） |
| state/latest.json が古い（取得が止まっている） | 予想は出す（古いことはダッシュボードに出る）。報告の先頭に書き、データ基盤チャットに直してもらう |
| git push がぶつかった | rebase を中止して報告。forecasts/ の記録はダッシュボードには書けているので、次回まとめて保存してよい |

## 止まったときの対応（設計書16-1）

| 症状（どこで気づくか） | まず確かめること | 携帯からの頼み方 | 頼むチャット |
| --- | --- | --- | --- |
| 担当に「停止の疑い」が赤く出た（ダッシュボード） | 定時実行の通知が届いたか | 「〇〇が停止の疑いです。原因を調べて直して」 | 🧭 司令塔 |
| 予想の更新が14時間以上止まっている（画面上部） | 最後に届いた通知の内容 | 「更新が止まっています。定時実行の状態を確認して」 | 🧭 司令塔 |
| 自動取得が「失敗」「古い」（自動取得の状況の欄） | どの取得先か | 「〇〇の取得が失敗しています。直して」 | 🗄️ データ基盤 |
| 代わりの取得先が24時間以上続く（画面上部） | どの項目か | 「〇〇が代わりの取得先のままです。一次データに戻して」 | 🗄️ データ基盤 |
| Google Cloudの予算アラートのメール | 金額 | 「予算アラートが来ました。原因を調べ、必要なら中継係を止めて」 | 🗄️ データ基盤 |
| 1週間後に上がる確率が前回から10ポイント以上動いた（通知の1行目） | 大きなニュースがあったか | 「予想が大きく動いた理由を説明して」 | 🧭 司令塔 |
| 画面が開かない・「データを読めません」 | 電波、サインイン | 開き直す。直らなければ「ダッシュボードが開きません」 | 🧭 司令塔 |

定時実行の中で起きた異常の頼み先：予想エンジンの失敗・ダッシュボードへの書き込みの失敗・GitHubへの保存の失敗は 🧭 司令塔、取得先のデータが古い・失敗は 🗄️ データ基盤。

**直すときの決まり**

- 直すのは、その部分の担当のチャットだけ。担当外のフォルダーは触らない。
- 原因と対処を、handoff.md に1行で記録する。
- 試運転中に定時更新の流れを直した場合は、7日を数え直す。取得先の一時的な障害（相手側の不具合）は数え直さない。
- 2回直しても直らない場合は、無理に続けず、その部分を止めて利用者に報告する。予想は取れたデータだけで続け、信頼度を下げて表示する。
- 金額にかかわる異常（予算アラート）は、原因がわかるまで中継係を止めることを優先する。
